## 2026-08-25: US-002 hardware encoding (NVENC + VAAPI) done

Implemented real hardware encode of captured frames via an ffmpeg subprocess
per session (stdin rawvideo bgra, stdout Annex B with -aud 1, AUs cut in
Rust). Chose subprocess over ffmpeg-next: box runs FFmpeg n9.0.1 (libavcodec
63), far newer than the crate supports, and subprocess needs no new packages
and survives FFmpeg upgrades. All four backend/codec combos verified at
2560x1440 60fps in/out.

## 2026-08-25: US-003 LAN transport done

Wire format v1 lives in agent/src/protocol.rs (new lib target) and
docs/protocol.md (repo root, written for the Swift client). Video: UDP
52800, AU fragmented into 1400B datagrams, 25B header (magic PHV, version,
BE u64 frame seq, BE u64 capture timestamp us, u16 frag index/count, flags
keyframe bit), all big-endian. Control: TCP 52801, length-prefixed (4B BE
len + 1B type), hello (codec/width/height/fps/bitrate/keyframe interval/
video port) on connect, keyframe_request from client. One client at a time,
new connection replaces old. Video is sent to the control peer's IP at the
negotiated port. Sequence numbers are assigned by the transport and stay
monotonic across encoder restarts.

FR-4: keyframe_request restarts the ffmpeg encoder session (fresh IDR next
AU). Measured restart: 100ms. protocol.md documents the tradeoff.

Verification (agent on the box, examples/receiver.rs on the Mac, over
Tailscale because UFW on the box blocks non-SSH LAN ports): ~60 AUs/s,
0.00% loss steady state, ffprobe on --dump output: h264 2560x1440. kbps is
low (~180 to 1100, alternating with the 2s IDR cadence) because the headless
desktop is static. Loss recovery proven both sides: receiver join and one
mid-stream loss each triggered keyframe_request, agent logged
"encoder restarted for keyframe request restart_ms=100", receiver recovered
to 60 fps 0.00% loss. Receiver restarts reconnect cleanly (new connection
replaces old).

Files changed:
- agent/src/lib.rs + agent/src/protocol.rs (new): wire format, fragment(),
  parse_datagram(), Reassembler (stale-frame sweep = loss), Hello
  encode/decode, control message framing; 6 unit tests incl. dropped
  fragment and out-of-order/duplicate cases.
- agent/src/transport/mod.rs: real control listener (accept loop, hello,
  reader thread per connection, ControlEvent mpsc) + VideoSender (fragment
  and send immediately, no buffering).
- agent/src/main.rs: pipeline wires capture -> encode -> transport; control
  events handled between frames; keyframe request restarts encoder via
  encode::create; capture-time FIFO pairs AUs to submitted frame instants.
- agent/examples/receiver.rs (new): reference receiver, --dump writes Annex
  B from first keyframe on.
- docs/protocol.md (new): the spec for the Mac client.

Learnings for future iterations:
- The box runs UFW; inbound LAN ports other than SSH are blocked and there
  is no sudo. Both machines are on Tailscale; run verification over the
  tailnet (box is 100.105.41.71, Mac 100.126.134.75). PRD already blesses
  Tailscale as LAN-like.
- ffprobe on raw Annex B reports r_frame_rate 120/1 for a 60fps nvenc
  stream (h264 timing is field-rate). Trust the AU count and the hello fps.
- Known race (v1-acceptable): a stale control reader can emit
  ClientDisconnected just after a new ClientConnected, clearing the live
  client target. Rare on LAN; fix with connection-tagged events if it ever
  bites the real client.

## 2026-08-25: US-005 hardware decode and live display on macOS done

Mac client now speaks wire protocol v1 (docs/protocol.md): TCP control via
NWConnection (hello parse, keyframe_request throttled to 1/s except forced on
join), UDP video via NWListener bound to the hello-negotiated port, fragment
reassembly with the protocol's receiver rules (500 ms stale sweep, sequence
gap means whole-frame loss, any loss is decode-fatal and waits for the next
IDR). VideoToolbox decodes Annex B access units; SPS/PPS are lifted from the
stream, a CMVideoFormatDescription is built with
CMVideoFormatDescriptionCreateFromH264ParameterSets, and the decode session is
rebuilt whenever the parameter set bytes change, which also covers encoder
restarts and resolution changes. Decoded NV12 CVPixelBuffers render through
the existing Metal surface via CVMetalTextureCache, aspect-fit with
letterboxing, YCbCr to RGB in the fragment shader. Test pattern stays as the
disconnected idle state. Chrome gained a host field and connect button, last
host persisted via @AppStorage (default 100.105.41.71), with auto-reconnect
on launch until US-012 owns it. Stats once per second to os_log and
/tmp/porthole-mac-stats.log: decoded fps, avg decode ms, loss %, queue depth.

Learnings for future iterations:
- VT session rebuild gotchas: format descriptions come from raw SPS/PPS NALs
  including the NAL header byte, start codes stripped; sample buffers must be
  AVCC (4-byte BE length per NAL) to match nalUnitHeaderLength 4. Rebuild on
  parameter set byte change, not on every keyframe: ffmpeg/NVENC repeats
  SPS/PPS per IDR, so naive rebuild-per-keyframe would thrash every 2 s.
- CMBlockBuffer: create with memoryBlock nil + default allocator, then
  CMBlockBufferReplaceDataBytes to copy the payload in; ownership stays clean.
- Xcode 26 SDK renames to watch: VTDecompressionSessionWaitForAsynchronousFrames
  (was ...ToComplete), CVMetalTextureGetTexture (was GetImage),
  CMSampleBufferCreateReady uses sampleTimingEntryCount/sampleSizeEntryCount.
- Color: the agent's ffmpeg/NVENC stream declares bt470bg (BT.601) limited in
  VUI even at 2560x1440; ffprobe confirms. Client honors VUI, else BT.709 for
  HD / BT.601 for SD. If text ever looks off, check what the encoder tags.
- Agent stream has 1:1 AU to frame ratio (no B-frames), so decode order equals
  presentation order; synchronous per-AU decode on a serial queue is enough
  and gives honest decode_ms measurement.
- AppleScript 'tell app Porthole to id of window' returns nothing for this
  SwiftUI app; find the window id via CGWindowListCopyWindowInfo matching
  kCGWindowOwnerName, then screencapture -l<id> works.
